### LLM

看了这 12 张场景图,我先把它们按"设备拓扑复杂度 + 交互模式"归了几类,因为这直接决定了用户会问什么类型的问题,不是随便瞎猜的:

场景分类

结合这几类,再对照行业里 VC 实际项目常问的问题维度(布局规划、节拍分析、效率分析、姿态分析、瓶颈工位识别这些是业内做仿真项目时反复出现的词),我把用户问题按执行阶段拆成三段来看,因为这决定了 Agent 该在哪个时间点主动问什么。

建模前 —— 用户一句话背后藏着的歧义,Agent 必须主动追问

拿场景 1(拆码垛)举例,用户很可能只说"让机器人把托盘上的物料放到传送带上",这句话里藏着至少四类信息缺口,分别对应不同的追问策略:

指代消歧:场景里如果有多台机械臂(如图 2、5、9),"机器人"指哪一台?这类问题不该每次都问——如果拓扑摘要(我们之前设计的 Topology Summarizer)显示只有一条路径能连通"托盘"和"传送带",Resolver 应该直接推断,而不是无脑追问打断体验。只有当拓扑图里存在多条同样合理的候选路径时才追问。
参数缺口:速度、节拍时间、抓取姿态这些数值型参数缺失时用默认值静默执行,还是必须追问——这里我建议分级:安全相关参数(比如安全围栏内机器人速度上限,对应图 11、12)绝不能用默认值静默带过,必须追问或至少显式告知用户"已按默认安全速度执行";非安全参数(比如传送带速度）可以静默用默认值,但要在终端日志里显式声明"已使用默认值 X",呼应白皮书里"VC 遇到参数缺失会静默执行、容易误导用户"这个颠覆点——我们不能重蹈覆辙,静默可以,但不能真的"无声"。
产品/物料类型不明确:图 1 的托盘上明显是多个相同零件,但图 9 那种机床场景,输入的毛坯和输出的成品往往是"同一个物理对象换了个状态",这种情况下 Agent 要能判断"这是同一物料的加工前后状态,不是两种物料"，不然工艺流程会被错误地建模成两条独立的物料流。
多工位路径歧义:图 3、6 这种环形/转台布局,产品从入口到出口可能有不止一条物理可达路径(比如经过工位 A 还是工位 B),用户说"让产品流转起来"这种模糊指令时,必须明确问清楚具体走哪条路径,这是不该省略的追问,因为不同路径对应完全不同的 SimPlan。
建模中/运行中 —— 用户打断怎么处理,这是你问题里最关键的一点

你说得对,用户不会只输入一句话就等着看完整仿真跑完。结合这 12 个场景,我想到几类真实会发生的打断场景,它们需要 Agent 用不同的方式响应,不能一刀切:

打断类型一:修正性打断("不对,应该是...")
比如仿真正跑到一半,用户发现图 9 里两台机床的上下料顺序反了,说"先加工左边那台"。这种打断本质是对当前 SimPlan 的局部修改,不需要重新走一遍完整的意图解析,应该：暂停仿真(对应 LangGraph 的 interrupt())→ 定位到 SimPlan 里对应的那条协调规则 → 增量patch → 询问是否从当前时间点继续还是重置重跑。这类打断的关键判断依据是:新指令引用的设备/参数,是否已经存在于当前激活的 SimPlan 里——如果是,走增量修改;如果引用了全新的、拓扑图里没有关联到当前产线的设备,那就不是修正,是下面这种情况。

打断类型二:完全新方案("不跑这个了,我想看另一个场景")
比如用户在图 6 那种多机械臂中心转台场景跑到一半,突然说"帮我模拟一下如果去掉一台机械臂会怎样"。这已经不是参数调整,是一个新的假设情景(what-if),需要判断这是要替换当前场景还是追加对比——这里我建议 Agent 不要自己猜,直接给用户一个选择而不是自然语言追问,因为这个决策点是离散的、有限选项的,适合用你们已经在做的 UI 组件(比如按钮式选择)而不是让用户再打一段话解释,这样交互成本更低。三个选项通常是:①在当前场景基础上修改后覆盖重跑 ②另存为新方案对比查看 ③丢弃当前仿真直接开始新的。这对应白皮书 Level 5"多轮迭代、命名保存仿真方案"那部分,但要补上"用户没主动说要保存"时 Agent 该怎么兜底的默认行为——我建议默认给一个自动命名的临时快照,而不是要求用户每次都手动决定要不要保存,不然打断的心智负担太重。

打断类型三:纯粹的观察性打断("等一下,先别动")
用户可能只是想暂停看清楚图 7 那种立体仓储里穿梭车具体怎么运动,并没有想改任何东西。这种打断 Agent 什么都不该做,只需要响应暂停/继续这类仿真控制指令,完全不该触发 Resolver 或任何 LLM 推理——这类指令应该在到达 Agent 图之前,就被前端的仿真控制条直接处理掉(白皮书里已经设计了播放/暂停/停止的 API),不要让每一次暂停都经过一次 LLM 调用,纯粹浪费延迟和成本。

这三类打断对 Agent 设计的实际启发是:打断处理的第一步应该是一个轻量分类器(可以是规则,也可以是一次很小的 LLM 调用),判断这次打断属于"控制类指令"、"对当前计划的修正"、"全新方案"三者之一,再分别路由到不同的处理子图,而不是让 Resolver 用同一套逻辑吞下所有打断类型。这本质上是我们之前聊的"图的自由度是设计出来的"这个原则的又一次应用——打断分类这一层应该是低自由度的确定性路由,具体怎么修正计划、怎么定义新方案的细节,才轮到 LLM 高自由度地发挥。

建模后 —— 结果导向的追问,容易被漏掉但很重要

跑完一次仿真后,用户大概率不会满足于看动画,而是会问节拍够不够、瓶颈在哪、能不能再加一台设备提升产能这类问题(这也是行业里做 VC 项目时被反复提到的"节拍分析""效率分析""瓶颈工位识别")。这意味着 Agent 在仿真结束后,不能只是被动等用户提问,而应该主动生成一份摘要式的复盘——白皮书里已经提到了 OEE 和瓶颈分析摘要,但结合这里的讨论,我觉得还应该补一类:主动给出可能的下一步假设情景建议,比如"当前仓储柜利用率已达 92%,是否要模拟增加一个货位分区后的效果"——这类建议不是必须执行的,而是给用户一个低成本的"要不要试试这个"的入口,减少用户自己想清楚该问什么的负担。

落回设计上的具体建议

结合以上讨论,我建议在现有 Resolver 之前,再加一个专门处理"打断"的入口分类节点(区别于处理首次输入的 Resolver),两者共享同一套拓扑摘要和 Skill 系统,但入口分类节点的职责只有一个:判断这一次用户输入是"新对话"还是"对正在运行/已完成仿真的打断",如果是打断,再判断是控制类、修正类还是新方案类,然后分别路由——控制类直接走 API 不进 LLM,修正类带着当前 SimPlan 的上下文进 Resolver 做增量解析,新方案类清空当前 SimPlan 上下文重新走完整流程。这样设计的好处是,不管用户是第一次说话还是说到一半打断,都不需要 Agent "全知全能地"在一个巨大的 Prompt 里处理所有可能性,而是先用确定性规则把问题范围收窄,再交给 LLM 精确处理。

这个设计思路是对的,而且刚好和 VC 自己的属性模型对上了——之前调研 `vcComponent.createProperty()` 时看到它支持给属性设 `MinValue`/`MaxValue`,这其实就是"默认值 + 合法范围"这套元数据模型的雏形,只是 VC 是工程师手写脚本时才这么干,我们是要把它做成设备库的标准 Schema,前置到设备入库阶段。基于这个方向,我想补充几个容易在实际做的时候踩坑的点。

# 2

## 一、"默认值"背后其实是两类性质完全不同的东西,不能用同一套机制处理

拿机械臂举例,"关节转角限制"和"传送带默认速度"看起来都是 Schema 里的一个字段,但语义完全不同:

- **物理硬约束**(关节转角限制、升降台行程范围):这是设备**物理上不可能超越**的边界,不是"默认值",而是"合法区间的边界本身"。这类参数不应该出现在"用户提及才会改"的逻辑里——用户永远不能把关节转角改到物理限位之外,不管提没提及。它的角色是校验用的上界/下界,应该直接喂给 Guardian 节点做硬校验,而不是 LLM 生成参数时可以自由覆盖的默认值。
- **业务/工艺默认值**(传送带速度、升降台移动速度):这是"没人特别要求时,给个合理的经验值",用户明确提及时可以覆盖,但覆盖后仍要落在物理硬约束的区间内。

所以我建议 Schema 分两层字段,别混在一起:

```json
{
  "device_type": "conveyor",
  "hard_constraints": {
    "Speed": { "min": 0.05, "max": 2.0 },
    "ConveyorLength": { "min": 0.5, "max": 20.0 }
  },
  "default_params": {
    "Speed": 0.4,
    "StartOffset": 0,
    "EndOffset": 0
  },
  "safety_critical_params": ["Speed"]
}
```

`hard_constraints` 交给 Guardian 做校验(不管值从哪来,超了就拒绝),`default_params` 才是"用户没提就用这个"的那部分,`safety_critical_params` 标记出即便要用默认值也不能静默、必须在日志里显式声明的那一小撮参数——这个字段其实就是回应我们之前聊的"静默但不能真的无声"那个原则,具体哪些参数算 safety_critical,由 Schema 逐设备类型声明,而不是写死在 Agent 逻辑里,这样新增设备类型时不用改代码。

## 二、"用户提及才改"这句话里,还藏着一个容易漏掉的时间维度

"只有用户提及才会更改"在单轮对话里没问题,但结合我们之前聊的打断场景就会暴露一个问题:**如果用户在第 3 轮对话里说过一次"传送带速度设成 0.6",到了第 8 轮用户又说"帮我改一下升降台的目标格位",这次 Device Modeler 重新生成 `process_config` 时,传送带的速度该读 Schema 默认值(0.4),还是读用户在第 3 轮说过的 0.6?**

如果每次生成都单纯"读 Schema 默认 + 本轮用户提及的覆盖",会把用户之前显式设置过的值悄悄冲掉——这比 VC 静默用默认值还糟,因为用户会觉得"我明明改过,怎么又变回去了"。所以这里需要在 Schema 的默认值之上,再加一层**实例级别的"当前生效值"**,类似:

```
device_type.default_params        ← Schema 静态默认(设备库层面,所有实例共享)
        ↓ 实例化时拷贝一份
instance.effective_params         ← 该实例当前生效值(初始 = default，用户改过的字段被标记覆盖)
        ↓ 每轮对话
instance.effective_params.Speed = 0.6  (source: user_stated, turn: 3)
```

之后每次 Device Modeler 生成新的 `process_config`,应该以 `instance.effective_params` 为基线,而不是每次都从 `device_type.default_params` 重新出发——这样"用户提及才改"这条规则实际上变成了"改一次,除非用户再次明确要求改回去,否则一直生效",这才符合用户的直觉预期。这个 `source` 字段(user_stated vs schema_default)顺带也解决了终端日志"哪些参数是用户设的、哪些是系统默认的"这个可追溯性需求。

## 三、Schema 变更的版本问题

设备库的 Schema 本身也会迭代(比如后续给传送带默认速度从 0.4 调成 0.5),但如果一个项目里已经实例化了 50 个传送带,Schema 更新不应该反向影响这些已经在跑的实例——`instance.effective_params` 在实例化那一刻应该是**深拷贝**而不是引用,后续 Schema 变化只影响新拖入场景的设备。这个点现在提前想清楚,能避免以后设备库迭代时线上项目参数突然"莫名其妙变了"的诡异 bug。

一句话总结这三点:**Schema 提供的是"类型层面的默认值和边界",但真正驱动 Agent 生成参数的应该是"实例层面、带来源标记、跨轮次持久化"的有效值**,Schema 本身只在两个时刻被读取——设备第一次拖入场景做初始化时,以及 Guardian 做边界校验时。

# 3关于可能的算法

这个问题问到了整套方案里一个真正的研究缺口——VC 本身完全不需要处理这个问题(它没有自然语言层,用户直接在 3D 视口里点选设备,不存在"左边那台是谁"这种歧义),所以查文档也查不到现成答案,这块得靠我们自己设计。我把这个问题拆成"参照系是什么"和"怎么算"两层来讲。

## 一、"左右"从来不是一个绝对方位,得先确定它相对谁

这句话背后其实有三种可能的参照系,必须先分清楚,因为它们给出的答案会完全不同:

1. **世界坐标系**(我们目前拓扑图用的那套):设备的 `pose.position` 是固定的世界坐标,和相机怎么转无关。但用户说"左边"时脑子里想的显然不是"X 轴负方向",而是"我现在看屏幕时,左手边那个"——这两者只有在相机恰好朝向某个特定角度时才会重合,你转一下视角这套映射立刻失效。
2. **相机/视口坐标系**(用户此刻实际看到的):这才是"左右"真正的参照系——它是**动态的、跟着用户操作实时变化的**,这也是你问题里点出的核心矛盾:拓扑图是静态算出来的场景结构,但空间指代词是"此时此刻这一帧画面"里才成立的关系。
3. **物料流方向系**(以工艺流向为"前后"定义出的相对左右,类似人站在产线旁边,面朝物料流动方向时的左右手):这套参照系的好处是**和相机无关、天然稳定**,但只在用户使用"上游那台""靠近入口那台"这类流向相关表述时才好用,不能覆盖所有"左右"的说法。

**结论是这三套都要留,但用途不同**:世界坐标系是拓扑图和 Guardian 校验的底层数据,不给用户用;物料流方向系应该在产品设计上被鼓励(比如追问时优先引导用户说"上游/下游"而不是"左边/右边",因为这个表述稳定、消歧成本低);但用户就是会说"左边那台",这时候唯一能解出正确答案的,是第二种——**必须知道用户说这句话的那一刻,相机在哪、朝向哪**。

## 二、具体怎么算:把三维位置投影到当前屏幕空间,而不是在三维里算方位向量

这一步的关键工程动作是:**前端每次用户发消息时,把当前相机状态作为消息的一部分元数据一起发给后端**,而不是只发文字。这在 React Three Fiber 里成本很低——`camera.position`、`camera.matrixWorld`(或者更精简一点,只传 `position` + `target`/lookAt 点 + `up` 向量)本来就是 Three.js 相机对象自带的,每次发消息时序列化一份附带上去就行,数据量很小。

拿到相机状态之后,不建议在三维空间里算"设备在相机右手边还是左手边"这种向量点积(这种算法在相机接近俯视/斜视角度时很容易出直觉相反的结果),更稳妥、也更符合用户实际视觉感受的做法是**直接做透视投影**:

```
对候选设备列表(比如图 9 里两台机床)中的每一台:
  screen_pos = camera.project(device.world_position)   # Three.js 自带方法
  # screen_pos.x 落在 [-1, 1]，对应归一化设备坐标里的屏幕横向位置
  # -1 是屏幕最左侧，+1 是屏幕最右侧

候选设备按 screen_pos.x 排序：
  x 更小(更靠负)的那个 → "左边那台"
  x 更大的那个 → "右边那台"
```

这一步和我们之前反复强调的原则一致——**这是纯几何计算,一次矩阵投影,不该也不需要 LLM 参与**,LLM 只在"识别出用户说了左边/右边,需要触发这次投影计算"这一步起作用,真正判断谁是左边完全交给确定性代码。

## 三、几个必须处理的边界情况

**候选集合从哪来**:光有相机状态还不够,"左边那台"这句话本身没说清楚是在两台机床里选,还是在全场景所有设备里选——这个候选范围必须从对话上下文/当前 SimPlan 里来(比如用户上一句刚提到"两台机床的上下料顺序",候选集合就该被收窄成这两台),而不是每次都对全场景所有设备做投影排序。这也是为什么这套机制必须挂在 Resolver 节点、而不是独立跑,它需要拓扑摘要 + 对话历史共同框定候选范围,相机投影只是最后一步消歧,不是从头找目标的手段。

**投影结果太接近怎么办**:如果相机几乎正对着两台设备的连线方向看过去(比如从机床 A 到机床 B 的方向恰好和相机视线平行),两者投影后的 `screen_pos.x` 会非常接近,这时候强行选一个风险很高。应该设一个置信度阈值——投影 x 差值小于阈值时,不要猜,直接追问"你是指靠近传送带入口的那台,还是靠近出口的那台"(退回用流向来消歧,因为流向和相机无关,总能给出确定答案)。

**要不要每次都主动确认解析结果**:即使投影计算给出了明确答案,考虑到这是一个基于"用户此刻恰好在看哪"的概率性推断,一旦相机在用户打字过程中被别人(多人协同场景下)或用户自己不小心转动过,结果就可能和用户本意不符。所以我建议 Agent 在执行任何不可逆操作前,把解析结果**回显**出来而不是直接默默执行,比如在终端日志或对话里先说一句"已将'左边那台'解析为 CNC_02,如果不对请告诉我",这个做法和我们之前讨论的"安全参数不能静默"是同一个原则的延伸——概率性推断的解析结果,同样不该完全静默地被消费掉。

**相机状态该什么时候发**:不需要只在检测到"左右前后"这类词时才发,建议每条用户消息都附带当前相机快照,当作和拓扑摘要同级别的上下文数据,反正数据量很小——是否用得上这份相机数据,交给 Resolver 判断,而不是在前端做文本关键词检测来决定要不要发送,那样会漏掉很多没有明说方位词、但其实隐含视角相关表达的情况(比如"这个""这一台"配合鼠标悬停/点选,其实也是一种视角相关的指代,只是不是文字层面的左右前后)。

一句话总结:**空间指代消歧的本质是"给 LLM 一份此刻的屏幕投影结果"而不是"让 LLM 理解三维空间"**——LLM 永远不擅长做几何推理,我们要做的是把"用户此刻在看什么"这件事先用确定性代码转换成结构化的、和屏幕位置对应的候选排序,LLM 只负责在这份已经排好序的候选里,结合对话意图挑一个,和之前拓扑理解那一层的设计思路完全同构。
